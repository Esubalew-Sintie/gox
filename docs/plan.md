# gox v2: design and implementation plan

Status: proposed on 2026-11-10; layout replaced on 2026-11-11 with the tree supplied by the project owner, modelled on the `initiator` package of an existing production service. Awaiting agreement. Nothing in this document is implemented.
Research behind every choice: [research/README.md](research/README.md).

## 1. Product definition

gox is a code generator, not a framework. One command creates a Go service in a hexagonal layout with the chosen database and infrastructure; a Clean Architecture rename of the same tree follows after v1.0. One command adds a feature with every layer and all of its wiring. Everything gox emits is ordinary Go that compiles, tests, and belongs to the developer. gox never runs inside the application.

Principles, in priority order:

1. **Explicit over magical.** Dependencies are constructor arguments in a generated composition root. No reflection containers, no `init()` registration, no blank imports.
2. **Ownership is explicit.** A file is tool-owned and regenerated every run under a `// Code generated by gox. DO NOT EDIT.` header, or user-owned and written exactly once, or one of the seven codemod files in which gox only appends or removes its own declarations (section 4.1.1). Nothing else is ever edited.
3. **Every command is idempotent and reversible.** Running a command twice is a no-op. `destroy` and `remove` undo `gen` and `add` from the manifest, never by searching code.
4. **Generation is verified or rolled back.** Writes are planned in memory, applied atomically, then `go build` and `go vet` must pass or the project is restored.
5. **Minimal by default.** The domain layer depends on the standard library only. Every library in a generated project is there because the developer chose a capability that needs it.
6. **Architecture is asked, implementation is decided.** The developer picks layout, database, transport and capabilities. gox decides file names, package names, mapping code, error handling, tests and wiring.

## 2. Generation model

gox keeps two files in the project root.

**`gox.yaml`** is user-editable intent. It is the only input gox needs to regenerate every tool-owned file.

```yaml
version: 2
module: github.com/acme/orders
arch: hexagonal          # the only value in v1.0; clean follows later
http: chi                # chi | stdlib
db: postgres             # postgres | mysql | sqlite | mongo | memory
capabilities: [redis, kafka]
features:
  - name: fleet
    fields: [name:string, capacity:int, status:string]
    transports: [http]
```

**`.gox/manifest.json`** is tool state. For every file gox has written it records the path, class (`tool`, `once` or `codemod`), template id, the declarations it added to a codemod file, gox version, and the SHA-256 of the content as written. This is what makes `destroy`, `check`, `upgrade` and clobber detection possible. The precedent is Kubebuilder's PROJECT file and openapi-generator's FILES list.

The internal model has seven concepts: Project, Feature, Domain, Service, Storage, Handler, and Capability. Presets map the model to directories and package names; they do not change the model or the wiring.

## 3. Layout

The layout is the one supplied by the project owner on 2026-11-11. The `app` package follows the `initiator` package of an existing production service: one file per concern, an `Init*` function per file, and a single entry function that calls them in order. gox generates exactly this shape. Column two marks who owns the file after generation: `once` is written one time and belongs to the developer, `tool` is regenerated on every run under a `// Code generated by gox. DO NOT EDIT.` header, and `codemod` is a developer-owned file in which gox only appends, or removes, its own declarations, map entries or struct fields.

Three things from the previous revision are gone at the project owner's request: `internal/config/app.go`, so `config.go` is a codemod file (4.1.1); `internal/domain/<feature>/errors.go`, so every error is in `internal/domain/errors.go`; and `internal/storage/postgres/db/`, replaced by the three files above. `externalapi/` is the sample service's `platform/` folder, renamed by the project owner; the folder and the package clause now share the name. The supplied list shows the provider folder as `externalapi/externalapi/`, which is read as a placeholder: a package named `externalapi` inside package `externalapi` would force an import alias in every file that uses both, so `gen client <name>` names the folder after the provider, `externalapi/corebank/`.

Dependency rule, enforced by a generated depguard configuration:

| Package | May import |
|---|---|
| `internal/domain` | standard library only |
| `internal/storage`, `internal/service`, `internal/handler` (the interface files) | `domain` |
| `externalapi/externalapi.go` | `domain` |
| `externalapi/<provider>` | `domain`, `externalapi`, `config` |
| `internal/service/<feature>` | `domain`, `storage`, `service`, `externalapi` (interfaces only) |
| `internal/handler/http/...` | `domain`, `service`, `handler` |
| `internal/storage/...` | `domain`, `storage`, `config` |
| `app` | everything |
| `internal/testutil` | `domain`, `storage` |

Service implementations depend on storage and externalapi interfaces, never on `internal/storage/postgres` or `externalapi/corebank`. Handlers depend on service interfaces, never on `internal/service/<feature>`. This is what makes the composition root the only place that knows concrete types.

### 3.6 Where each kind of code lives

| Thing | Location |
|---|---|
| Entity for a feature | `internal/domain/<feature>/<feature>.go`: struct, `New` with invariants, value objects; imports only `domain` |
| Shared entity | `internal/domain/<name>/`, created with `gox gen domain <name>` |
| Enum tied to one entity | the entity's package, `type Status string` plus constants |
| Enum shared across features, shared value objects | `internal/domain/*.go` in package `domain` (`Platform`, `Money`, `Page`) |
| Errors, all of them | `internal/domain/errors.go`: `ErrorType` constants, `errors.New` sentinels, `ErrorMap`, `ErrorTypeMap`, see 3.7; `gen feature` and `gen client` append their entries, prefixed `ErrFleet*`, `ErrCoreBank*` |
| Service inputs | `internal/domain/<feature>/`: `CreateInput`, `UpdateInput`; services never take HTTP DTOs |
| Domain events | `internal/domain/<feature>/events.go` |
| Timeouts, TTLs, limits, topics | `config.yaml` and `internal/config/config.go`, never constants |
| HTTP DTOs | `internal/handler/http/<feature>/dto.go` with `toInput` and `toResponse` |

| SQL, table names | inside the repository file |

### 3.7 Response contract, taken from the sample service

The sample writes every HTTP response through two functions, one for success and one for error, and never lets a handler build JSON by hand. gox keeps that contract, keeps the sample's `ErrorMap` and `ErrorTypeMap` in one `errors.go` as the sample has them, and removes `ErrorCodeMap`. The complete folder, with every file compiled and tested, is in [errors-and-response.md](errors-and-response.md); this section is the summary.

**Success**, status 200 for reads and updates, 201 for creates. `meta` is present only for lists.

```json
{
  "status": 200,
  "message": "Fleets fetched successfully",
  "data": [ { "id": "…", "name": "North", "capacity": 12, "status": "ACTIVE" } ],
  "meta": { "total_docs": 25, "limit": 10, "total_pages": 3, "page": 1, "paging_counter": 1,
            "has_prev_page": false, "has_next_page": true, "next_page": 2 },
  "has_retry": false
}
```

**Business or infrastructure error.** `status` comes from `ErrorMap`, `type` from `ErrorTypeMap`, `message` is the matched error's text. There is no `code` or `name`.

```json
{
  "status": 404,
  "error": { "type": "not_found", "message": "Fleet not found." },
  "has_retry": false
}
```

**Validation error.** `message` is the first field error, as the sample does, and `details` lists all of them.

```json
{
  "status": 400,
  "error": { "type": "validation", "message": "name cannot be blank",
             "details": [ { "field": "name", "description": "name cannot be blank" } ] },
  "has_retry": false
}
```

**Unknown error.** Anything not in the maps becomes `ErrInternalServerError`: `500`, `internal`, fixed message. The raw error text never reaches the wire; it goes to the log with the request id.

The catalogue is the sample's shape, one file; `gox gen feature fleet` appends the fleet block and map lines:


The writers and a generated handler, which reads the same as the sample's handlers:

```go
// internal/handler/http/response/response.go
func Success(w http.ResponseWriter, r *http.Request, status int, message string, data any, opts ...Option) // WithMeta(m), WithRetry()
func Error(w http.ResponseWriter, r *http.Request, err error, opts ...Option)

// internal/handler/http/fleet/handler.go
func (h *fleetHandler) Create(w http.ResponseWriter, r *http.Request) {
	var req createFleetRequest
	if err := request.Decode(r, &req); err != nil { // 1 MiB limit, unknown fields rejected, req.Validate() run
		response.Error(w, r, err)
		return
	}
	out, err := h.service.Create(r.Context(), req.toInput())
	if err != nil {
		response.Error(w, r, err)
		return
	}
	response.Success(w, r, http.StatusCreated, "Fleet created successfully", toResponse(out))
}
```

`response.Error` does, in order: resolve the error through the two maps with `domain.Lookup`, which walks the wrap chain; fall back to `ErrInternalServerError` when nothing matches; take the message from the matched entry, or from the first field of a `*domain.ValidationError`; compute `has_retry` with `domain.Retryable`; log once at error for `internal`, warn for `unavailable`, `timeout` and `external_service`, info for client types, with request id and the full error text; encode to a buffer, then write headers and body once. Validation errors are already `*domain.ValidationError` by the time they reach the writer, because `request.Decode` is the only code that sees ozzo.

How each layer produces errors, so the mapping holds end to end:

| Layer | Rule |
|---|---|
| domain | the entity package imports `domain` and returns its errors (`domain.ErrFleetInvalidCapacity`); every error is in `internal/domain/errors.go` |
| storage/postgres | `postgres.Translate(err, domain.ErrFleetNotFound)`: no rows to the given not-found error, unique violation to `ErrConflict`, foreign key and check to `ErrInvalidData`, deadlock and serialization to `ErrConcurrentUpdate`, deadline to `ErrRequestTimeout`, connection failure to `ErrServiceUnavailable`, anything else to `ErrInternalServerError`; every one carries the pgx error as cause |
| externalapi | upstream status and body to a catalogue entry with `domain.Wrap`; `gen client corebank` appends `ErrCoreBank*` entries to the same file |
| service | returns errors unchanged or wraps with `fmt.Errorf("send fleet: %w", err)`; wrapping is safe because `Lookup` walks the chain |
| handler | never inspects errors, always `response.Error` |
| middleware | auth failures return `domain.ErrUnauthorized` or `domain.ErrForbiddenRequest`; the recovery middleware turns panics into the unknown shape |

What this changes relative to the sample, each because the sample's own code showed a defect:

- `ErrorCodeMap` is removed. In the sample nearly every entry collapses to `GEN_019 VALIDATION_FAILED` or one of six `REM_` codes, so `code` and `name` told the client nothing the `type` did not. The two remaining maps are kept as the team writes them.
- The sample looks the bare error value up, so a wrapped error misses the maps and every layer has to return sentinels without context. `domain.Lookup` walks the wrap chain, so services can wrap and the cause reaches the log.
- The sample's local writer returns `err.Error()` of any unmapped error as `400 bad_request`, which exposes driver and network text. The shared library sanitises with a substring list in which `:` matches almost every message. gox returns `ErrInternalServerError` with its fixed message instead.
- `ErrInternalServerError` maps to 400 in the sample. It maps to 500 here.
- The sample's two maps can drift, and do: entries exist in one map but not the other. gox always writes both lines together, and the generated `TestMapsAgree` fails if they ever disagree.
- The sample's encode-failure path calls `WriteHeader` twice, which the second time is a no-op. gox encodes to a buffer first.
- Success is always 200 in the sample. gox uses 201 for create.
- Per-handler metric and span recording in the sample becomes route-level middleware; audit spans with business fields stay hand-written in the handler, where the sample has them.

The USSD branch of the shared writer, which substitutes request and response into `meta` for one channel, is not generated; `Option` is the extension point for it.

## 4. Wiring design

### 4.1 The composition root mirrors the sample `initiator`, with a fixed seam between developer code and generated code

`app` holds the whole dependency graph as explicit `Init*` calls. The developer-owned `app.go` is the only file that knows the order. Everything that changes when a feature or capability is added lives behind seven generated functions whose signatures never change after `gox new`: `InitInfra`, `InitExternalAPI`, `InitStorage`, `InitCache`, `InitService`, `InitHandler`, `InitRoutes`.

```go
// app/app.go  (once, developer-owned; shown as generated by gox new)
package app

func Initialize(ctx context.Context) error {
	cfg, err := InitConfig(ctx)
	if err != nil {
		return err
	}
	log := InitLogger(cfg)

	infra, err := InitInfra(ctx, cfg, log)            // generated: postgres, redis, kafka ...
	if err != nil {
		return err
	}
	defer infra.Close(context.Background(), log)

	externalAPI := InitExternalAPI(cfg, infra, log)    // generated: external API clients
	storage := InitStorage(infra, log)                 // generated
	cache := InitCache(infra, log)                     // generated, empty until gox add redis
	service := InitService(storage, cache, externalAPI, infra, cfg, log) // generated
	handler := InitHandler(service, log)               // generated

	r := chi.NewRouter()
	r.Use(middleware.Recovery(log), middleware.Logger(log))
	InitRoutes(r, handler)                             // generated

	return serve(ctx, cfg, r, log)                     // developer-owned: http.Server, signal.NotifyContext, Shutdown
}
```

```go
// app/infra.go  (tool)
// Code generated by gox. DO NOT EDIT.
type Infra struct {
	Postgres *pgxpool.Pool
	Redis    *redis.Client
	Kafka    *kgo.Client
}

func InitInfra(ctx context.Context, cfg *config.Config, log *slog.Logger) (Infra, error) {
	var i Infra
	var err error
	if i.Postgres, err = InitPostgres(ctx, cfg.Postgres, log); err != nil { return i, err }
	if i.Redis, err = InitRedis(ctx, cfg.Redis, log); err != nil { return i, err }
	if i.Kafka, err = InitKafka(ctx, cfg.Kafka, log); err != nil { return i, err }
	return i, nil
}

func (i Infra) Close(ctx context.Context, log *slog.Logger) { CloseKafka(...); CloseRedis(...); ClosePostgres(...) }

// app/external_api.go  (tool)  external APIs, as in the sample's initiator/platform.go
type ExternalAPI struct {
	CoreBank externalapi.CoreBank
}

func InitExternalAPI(cfg *config.Config, i Infra, log *slog.Logger) ExternalAPI {
	return ExternalAPI{
		CoreBank: corebank.New(cfg.ExternalAPI.CoreBank, i.Redis, log),
	}
}

// app/storage.go  (tool)
type Storage struct {
	Fleet storage.FleetRepository
	User  storage.UserRepository
}

func InitStorage(i Infra, log *slog.Logger) Storage {
	return Storage{
		Fleet: fleetpg.New(i.Postgres, log),
		User:  userpg.New(i.Postgres, log),
	}
}

// app/service.go  (tool)
type Service struct {
	Fleet service.FleetService
}

func InitService(s Storage, c Cache, e ExternalAPI, i Infra, cfg *config.Config, log *slog.Logger) Service {
	return Service{Fleet: fleetsvc.New(s.Fleet, e.CoreBank, log)}
}

// app/handler.go  (tool)
type Handler struct {
	Fleet handler.FleetHandler
}

func InitHandler(s Service, log *slog.Logger) Handler {
	return Handler{Fleet: fleethttp.New(s.Fleet, log)}
}

// app/routes.go  (tool)

	r.Route("/api/v1", func(r chi.Router) {
		handlerhttp.Register(r, h.Fleet.Routes())
	})

```

`InitPostgres`, `InitRedis` and `InitKafka` live in their own developer-owned files so pool sizes and client options can be tuned by hand. `gox add kafka` creates `app/kafka.go` and regenerates `infra.go`; `gox remove kafka` deletes `kafka.go` if its hash is unchanged and regenerates `infra.go`. `gox gen client corebank` creates `externalapi/corebank/`, appends the `CoreBank` interface to `externalapi/externalapi.go`, appends `ExternalAPI.CoreBank` to `internal/config/config.go`, and regenerates `app/external_api.go`. Health and readiness are registered in `InitRoutes` from the clients present in `Infra`, the same way the sample's `ReadinessHandler` checks Oracle, Redis and Kafka.

### 4.1.1 The interface files, the error catalogue and the config struct are the only codemod gox performs

`internal/storage/repository.go`, `internal/storage/cache.go`, `internal/service/service.go`, `internal/handler/handler.go` and `externalapi/externalapi.go` are developer-owned because the developer adds business methods to them. gox touches them in exactly two ways: `gen feature` appends one `type XxxInterface interface { ... }` declaration, and `destroy feature` removes that declaration by name. Both operate on whole top-level declarations through `go/ast` and `go/format`, which is well-defined because a declaration's doc comment belongs to the declaration. This is deliberately not the import-spec surgery of the current injector, whose comment-stranding defect was reproduced during research. Appending never conflicts with developer edits; removal is refused if the declaration's method set no longer matches the manifest, and the file is listed for manual cleanup.

`internal/domain/errors.go` is the sixth codemod file, because the project owner keeps every error in one file as the sample service does. `gen feature fleet` appends one `var ( ErrFleet... )` block after the last var block and one `KeyValueExpr` per error at the end of the `ErrorMap` and `ErrorTypeMap` composite literals, each group under a `// Fleet` comment; `gen client corebank` does the same with `ErrCoreBank*`. `destroy` removes exactly the identifiers recorded in the manifest: the var block, and the map entries whose key is one of those identifiers. Entries the developer added, including ones named `ErrFleet*`, are not in the manifest and stay. Removal of an entry whose value differs from what gox wrote is refused the same way as a changed interface. The generated `TestMapsAgree` keeps the two maps in step regardless of who edited them.

`internal/config/config.go` is the seventh. `gox new --db postgres`, `gox add redis` and `gox gen client corebank` each append one `type PostgresConfig struct { ... }` declaration with `koanf` tags and one field on `Config` (`Postgres PostgresConfig` with tag `koanf:"postgres"`), and add the matching keys to `config.yaml` and `.env.example`. `gox remove` takes them out by name. Types and fields you add are untouched, which is why there is no separate file for your own settings.

### 4.2 Startup flow and request flow

These are two different graphs. `app` is on the first and not on the second.

**Startup.** What `app.Initialize` builds, in order. Each `Init*` in `app` calls the feature package's `New` and hands the next layer only what it needs: the repository gets the pool, the service gets `storage.FleetRepository`, the handler gets `service.FleetService`. Nothing below `app` ever sees the `Infra`, `Storage`, `Service` or `Handler` structs.

```text
cmd/main.go                   app.Initialize(ctx); exit 1 on error
└─ app/app.go                 the only file that knows the order (developer-owned)
   ├─ app/config.go           InitConfig: koanf reads config.yaml, then env ─► internal/config/config.go  Config
   ├─ app/logger.go           InitLogger: slog JSON handler, set as slog.Default
   ├─ app/infra.go            InitInfra ─► app/postgres.go InitPostgres ─► internal/storage/postgres/postgres.go NewPool ─► *pgxpool.Pool
   │                                    ─► app/redis.go InitRedis, app/kafka.go InitKafka, when added
   ├─ app/external_api.go     InitExternalAPI ─► externalapi/corebank New(cfg.ExternalAPI.CoreBank, infra.Redis, log)
   ├─ app/storage.go          InitStorage ─► internal/storage/postgres/fleet New(infra.Postgres, log)   storage.FleetRepository
   ├─ app/cache.go            InitCache ─► internal/storage/redis New(infra.Redis, log)                     storage.FleetCache
   ├─ app/service.go          InitService ─► internal/service/fleet New(storage.Fleet, externalAPI.CoreBank, log)   service.FleetService
   ├─ app/handler.go          InitHandler ─► internal/handler/http/fleet New(service.Fleet, log)         handler.FleetHandler
   ├─ app/routes.go           InitRoutes ─► r.Route("/api/v1", ...) mounts handler.Fleet.Routes(); health and readiness from Infra
   └─ serve                   http.Server, signal.NotifyContext, Shutdown; then infra.Close in reverse order
```

The object graph in memory when `Initialize` reaches `serve`:

```text
PostgreSQL ◄── *pgxpool.Pool ◄── fleet repository   internal/storage/postgres/fleet   implements storage.FleetRepository
                                       ▲
                                       │ repo
                                 fleet service      internal/service/fleet            implements service.FleetService
                                       ▲
                                       │ service

                                       ▲
                                       │ Routes()

```

**Request.** `POST /api/v1/fleets`. The interface files are not hops on this path; they are the compile-time contracts between the hops.

```text
HTTP request
  │  chi router, then internal/handler/http/middleware: request id, recovery, logger, auth
  ▼
internal/handler/http/fleet/handler.go      Create: request.Decode(r, &req)   1 MiB limit, unknown fields rejected, req.Validate() run
  │  req.toInput()                                  on failure: response.Error(w, r, err)  →  400 validation, first field as message
  ▼
internal/service/fleet/service.go           Create: fleet.New(...) ─► internal/domain/fleet/fleet.go enforces invariants
  │  s.repo.Create(ctx, f)                          through storage.FleetRepository (internal/storage/repository.go)
  ▼
internal/storage/postgres/fleet/repository.go   r.pool.Exec(...), or postgres.WithTx for Update
  │                                                 on error: postgres.Translate(err, domain.ErrFleetNotFound)
  ▼

```

And back:

```text
PostgreSQL
  ▼
repository.go    rows into the entity, or a catalogue error with the pgx error as cause
  ▼
service.go       returns unchanged, or fmt.Errorf("create fleet: %w", err)
  ▼
handler.go       response.Success(w, r, http.StatusCreated, "Fleet created successfully", toResponse(out))
                 response.Error(w, r, err): domain.Lookup walks the chain, ErrorMap gives the status, ErrorTypeMap the type
  ▼
HTTP response    {status, message, data, has_retry}   or   {status, error: {type, message, details?}, has_retry}
```

What this means for the generator: `gox gen feature vehicle` writes `VehicleRepository`, `VehicleService` and `VehicleHandler` with their `Init*` constructors, appends the three interfaces, then regenerates `app/storage.go`, `app/service.go`, `app/handler.go` and `app/routes.go`. `app/app.go` does not change, and no business logic enters `app`. Both diagrams are written into the generated `AGENTS.md`.

### 4.3 The contract between user code and generated code is a Go convention

Each generated package exposes stable entry points: a `New(...)` constructor returning the concrete type, a `var _ storage.FleetRepository = (*Repository)(nil)` assertion next to it, `Routes()` on HTTP handlers, and the same assertions in the fakes. The `app` package keeps the sample's `Init*` names for its own wiring functions, because that is the `initiator` shape the project owner asked for. gox knows these signatures because it wrote them and records them in the manifest. No marker comments exist anywhere in developer-owned code.

### 4.4 When the developer changes a constructor

This is the hardest problem for any wiring generator. Proposed answer, in two layers:

1. **Resolution by type.** Before regenerating the root, gox type-checks each feature package with `go/packages`, reads every `New` signature, checks with `types.Implements` that the returned type satisfies the interface field it is assigned to, and resolves each parameter by type against the known providers (`Infra`, `ExternalAPI`, `Storage`, `Cache`, `Service`, `Config`, logger). A parameter with no provider is an error that names the missing port and suggests `gox gen adapter`. This is deterministic, needs no annotations, and is the same resolution wire performed.
2. **Manifest fallback.** If a feature package does not type-check, gox regenerates from the signatures recorded in the manifest and prints the compiler error, so a broken package never blocks fixing the wiring.

`gox sync` runs this on demand; `gen` and `add` run it automatically.

### 4.5 Safety guarantees

- Tool-owned files are compared to the manifest hash before every write. A mismatch aborts with a diff unless `--force` overwrites or `--adopt` converts the file to user-owned.
- Developer-owned files are never rewritten after creation. `gox gen --force <path>` regenerates one file after showing the diff. The seven codemod files are only appended to or have gox's own declarations, map lines and struct fields removed, as described in 4.1.1.
- Deletions only touch files whose hash still matches the manifest; anything the developer edited is left in place and listed.
- Every command plans in a virtual tree, so `--dry-run` prints the transcript and diff without touching disk.
- Apply requires a clean git tree or `--allow-dirty`, writes through temp files and rename, runs `imports.Process` on every Go file, then `go build ./...` and `go vet ./...`. On failure the originals are restored.
- `gox check` regenerates to memory and exits non-zero on drift, for CI.

## 10. Decisions required

1. **Wiring mechanism.** Replace marker injection with the generated `app` package of section 4.1 (seven tool-owned files with fixed signatures, developer-owned `app.go` and per-client files), a manifest with hashes, and type-based resolution for edited constructors. Recommended: yes.
2. **Layout.** The tree in section 3.1 exactly as supplied on 2026-11-11 (second revision): `externalapi/` without the hyphen, `config.yaml`, `AGENTS.md`, `.golangci.yml` and `.env.example` at the root, middleware under `internal/handler/http/`, storage interfaces split into `repository.go`, `cache.go` and `publisher.go`, one `internal/domain/errors.go`, a single `internal/config/config.go`; plus the three Postgres helper files called out below the tree, and the placement rules of section 3.6. Retire `layered-rest` and `feature-first` now; bring `feature-first` back as `--group-by module` later.
3. **Interface files.** Keep `storage/repository.go`, `storage/cache.go`, `service.go`, `handler.go` and `externalapi.go` as single files that gox appends to and removes declarations from (section 4.1.1). Alternative: one interface file per feature (`internal/storage/fleet.go`), which needs no codemod at all but changes the supplied tree.
4. **Constructor naming.** Decided 2026-11-11: `New` returning the concrete type, with a compile-time interface assertion beside it. `app/` keeps `Init*` for its wiring functions.
5. **Clean preset.** Decided 2026-11-11: hexagonal only in v1.0; clean follows as the rename-only preset of section 3.2.
6. **HTTP.** chi v5 as default because the supplied tree and the sample service use it; stdlib `ServeMux` as the alternative. OpenAPI as an opt-in capability.
7. **Databases for v1.** Decided 2026-11-11: postgres, mysql, sqlite, mongo and memory; SQL written in repositories; golang-migrate pairs as in the supplied `migrations/`.
8. **Library defaults.** Decided 2026-11-11: the table in section 6 with `go 1.26.0` and ozzo-validation; slog, franz-go, koanf and stdlib testing stay as listed.
9. **Command vocabulary.** The table in section 5; the generation unit is `feature`; the field DSL as specified.
10. **Rewrite, not extend.** The engine is rebuilt and the current injector removed; version moves to 0.2.0 and reaches 1.0 at phase 6.
11. **Response contract.** The sample's envelope on both paths, resolved through `ErrorMap` and `ErrorTypeMap` in one `internal/domain/errors.go` with `ErrorCodeMap` removed, as in section 3.7, including 201 for create and a fixed message for unknown errors. Alternatives: keep 200 everywhere; RFC 9457 problem details instead of the envelope.
12. **v1.0 scope.** Decided 2026-11-11: phases 0 through 4.

## 11. Risks

- **Scope.** Five databases are the main template surface and all five are in v1.0 (decision 7); the SQL repository template must be dialect-parameterised so mysql and sqlite share the Postgres template. If phase 3 slips, mysql and sqlite move to 1.1 without touching anything else.
- **The codemod** is the one place gox edits developer-owned code. It is limited to whole top-level declarations, the map entries it added in `internal/domain/errors.go` and the struct fields it added in `internal/config/config.go`, and refuses to remove a declaration the developer has changed, so the worst case is a leftover interface that `gox doctor` reports.
- **Type-based resolution** is the most complex piece of the engine; it ships in phase 4 behind a manifest fallback so phases 2 and 3 do not depend on it.
- **Dependency health.** huma has one maintainer, sqlc has a large backlog, the ecosystem bumps minimum Go versions twice a year. Every default is behind a capability so it can be swapped.
- **Go 1.27 json/v2** changes generated API behaviour; a generated test makes the change visible before a project bumps its toolchain.
