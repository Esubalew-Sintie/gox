# ADR 0002: Three file classes, a manifest with hashes, verified atomic apply

- Status: accepted
- Date: 2026-11-11
- Plan: docs/plan.md, sections 2 and 4.5

## Context

The current generator finds its insertion points with marker comments and edits import specs by hand; research reproduced a defect where it strands comments. Commands must be idempotent, `destroy` must undo `gen` exactly, and gox must never overwrite a file the developer has edited without saying so. Kubebuilder's PROJECT file and openapi-generator's FILES list are the precedents for recording what a tool wrote.

## Decision

Two files live in the project root. `gox.yaml` is user-editable intent and the only input needed to regenerate every tool-owned file. `.gox/manifest.json` is tool state: for every file gox wrote, its path, class, template id, gox version, the SHA-256 of the content as written, and for codemod files the identifiers gox added.

Every generated file has one of three classes:

- **once**: written one time, then owned by the developer and never rewritten. `gox gen --force <path>` regenerates one such file after showing a diff.
- **tool**: regenerated on every run under a `// Code generated by gox. DO NOT EDIT.` header. Before a write the current hash is compared to the manifest; a mismatch aborts with a diff unless `--force` overwrites or `--adopt` converts the file to once.
- **codemod**: developer-owned, in which gox only appends or removes its own declarations (ADR 0005).

Every command plans in a virtual tree (create, regenerate, delete, identical, conflict) so `--dry-run` prints the transcript and diff without touching disk. Apply requires a clean git tree or `--allow-dirty`, writes through temporary files and rename, runs `imports.Process` on every Go file, then `go build ./...` and `go vet ./...`; on failure the originals are restored. Deletions only touch files whose hash still matches; anything edited is left in place and listed. `gox check` regenerates to memory and exits non-zero on drift.

## Consequences

- `.gox/manifest.json` must be committed with the project.
- A developer who wants to edit a tool file adopts it and takes over its maintenance; gox then stops regenerating it.
- `destroy` and `remove` are driven by the manifest, never by searching the code.
- The build-and-vet step makes every command slower than a plain file write. Accepted: a generated project that does not compile is the worst outcome.

## Alternatives considered

- **Marker comments** (current). Brittle under formatting and refactoring, and invisible in the file list. Rejected.
- **Regenerate everything and merge.** Three-way merges of developer code are error-prone; reserved as a later `upgrade` feature for once files only.
- **No manifest, detect ownership from headers.** Cannot detect edits to tool files or know what `destroy` should remove.
